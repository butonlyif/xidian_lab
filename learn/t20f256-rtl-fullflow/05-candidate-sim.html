CHAPTER 05

候选与仿真

candidate.deliver → verification.simulate → candidate.promote：候选被冻结、被真跑、被晋级。

本章目标

理解「候选」的不可变性（字节冻结 + digest 校验）、testbench 的 EVOVERSE_PROPERTY 事件协议， 以及 promote 之后基线长什么样。

STEP 1

冻结候选（candidate.deliver）

这一步在做什么：控制面把候选文件的字节读走、算 digest、存进不可变的 run 目录——从这一刻起，改一个字节都会被识破。

💬 对 Trae 说：
代码写完了，帮我提交审核。
翻车实录第一次提交被拦下了——控制面的「源闭合」检查报出五个 missing module， 而它们全是完全合法的 RTL。把报错原文丢给 Trae，它对着引擎源码逐条改写（语义不变）后重新提交，冻结通过。 报错原文与五处误伤的逐条修法见右栏两张修复卡。
✓ 词法修复后重新提交 · candidate.deliver ok
修复 · SOURCE_CLOSURE_INVALID 原文

第一次 candidate.deliver 被拦下的报错原文：

SOURCE_CLOSURE_INVALID: referenced missing module CNT_W; referenced missing module RESULT;
referenced missing module integer; referenced missing module seen_pos; referenced missing module step_cnt
知识 · candidate.deliver 的动作语义

candidate.deliver = 冻结：控制面把候选文件的字节读走、算 digest、存进不可变的 run 目录。 之后每一次验证都以这份冻结字节为准——你在工作树里再怎么改，都影响不了已提交的候选。

不可变性是后两步的前提：verification.simulate 亲跑的是冻结字节，candidate.promote 安装的也是冻结字节。 改一个字节都会被 digest 识破——想换内容，就走 candidate.repair 提交新候选，而不是偷偷改旧文件。

STEP 2

读懂「源闭合」检查的词法陷阱

这一步在做什么：控制面扫描候选 HDL 的模块引用闭合性。它的词法器只保留「标识符 + # ( ) ; , .」， 并把 标识符 标识符 ( 的序列当作模块例化——于是很多完全合法的 RTL 会「看起来像例化」。 五个误伤的对照表与逐条修法已放进右栏修复卡。

后面增量章节还会遇到同族陷阱：wire co0 = en0 && (d0==9) 的比较括号、 endcase 紧跟 if (、x = f( 型赋值——手法一致：调整括号/拆行/换写法，语义不变。

✓ 五处误伤全部改写 · 语义不变 · 冻结通过
修复 · 五个误伤逐条对照

五个误报逐一对应（修复手法都是官方推荐的外层括号或等价改写）：

误报的“模块”肇事的代码词法上变成修法
CNT_Wlocalparam int CNT_W = $clog2(N);CNT_W $clog2 (位宽声明里直接写 [$clog2(N)-1:0]，删掉这个 localparam
step_cntstep_cnt == CNT_W'(N-1)step_cnt CNT_W (去掉 sized cast：step_cnt == (N-1)
integerfunction integer f(...)integer f (返回类型写成 function [31:0] f(...)
seen_posseen_pos[pos_of(cur)] = 1;seen_pos pos_of (外层加括号：seen_pos[(pos_of(cur))] = 1;
RESULT字符串 "TB-RESULT: PASS ("RESULT PASS (（字符串不剥离！）文案改成 TB-RESULT.PASS (（逗号/句点是合法分隔符）
可能 · 同族陷阱预告

后续增量章节的同族案例（修法一致）：

wire co0 = en0 && (d0==9) 的比较括号、endcase 紧跟 if (、 x = f( 型赋值——调整括号 / 拆行 / 换写法，语义不变。

知识 · 经验沉淀

这不是要你背词法规则。让 Trae 修——把错误原文丢给它，它读引擎源码后给出的改法都是「语义等价 + 词法安全」的。

STEP 3

testbench 的事件协议：EVOVERSE_PROPERTY

这一步在做什么：控制面判 PASS 不看人读的 TB-RESULT 文案，只解析标准事件行并与 Test IR 的义务集合精确对账。

// 每项义务在达成点输出一行（propertyId 必须与规格追踪表里的 ID 完全一致）：
$display("EVOVERSE_PROPERTY {\"propertyId\":\"PROP-ONEHOT\",\"status\":\"pass\",\"artifactPath\":\"tb_marquee10\"}");

# 判定规则（来自引擎）：expected = {性质×requiredActivations} ∪ {判定器} ∪ {覆盖项}
#   全部满足 ≥ 次数 → all-pass；期望集外的 ID → incomplete-coverage；fail → assertion-mismatch

跑马灯基线的义务账单：PROP-RESET×1、PROP-ONEHOT×10、PROP-ROTATE×10、PROP-HOLD×5、 四个 ORC、两个 COV——testbench 在对应检查点逐一打点。本地先自测：

iverilog -g2012 -s tb_marquee10 -o sim/tb.vvp rtl/top.v rtl/marquee10.sv sim/tb_marquee10.sv
vvp sim/tb.vvp

TB-RESULT.PASS (160 samples, 39 rotations)      # 248 条事件全部 pass，$finish 退出码 0
翻车实录第一版 tb 的步进间隔检查失败过一次——根因是输出寄存让首次呈现多了固定 1 拍。 修正方式不是改 RTL，而是把期望写成「首转多 1 拍」并注释原因。FAIL 原文与逐条分析见右栏修复卡。
✓ 本地自测 PASS · 248 条事件全过 · $finish 退出码 0
修复 · 一个真实的时序发现

失败原文：

FAIL PROP-HOLD rotate=1 hold=5 exp=4

根因：输出寄存 led_out_r 让首次呈现多了固定 1 拍。

修法：不是改 RTL，而是把期望写成「首转 = STEP_CYCLES+1、后续 = STEP_CYCLES」并注释原因—— 规格要求的是相邻步进间隔精确，首拍的呈现延迟是合法行为。

STEP 4

控制面亲自仿真（verification.simulate）

这一步在做什么：控制面做的事远不止「跑一下」——它对冻结候选的身份、编译、运行、对账全程亲办（细节见右栏知识卡）。

💬 对 Trae 说：
跑一遍仿真看看结果。
ok:true  evidenceId: sim-6746d444dfe6  status: PASS  scope: CANDIDATE_SLICE
asset module:marquee10 → QUALIFIED
run 工件: .evoverse/control/artifacts/runs/<requestId>/  （compile/run stdout、events.json、summary.json）
✓ verification.simulate PASS · 证据 sim-6746d444dfe6
状态 · 仿真证据 ID 谱系

每次 verification.simulate 都会在控制面留下独立证据 ID：

sim-6746d444dfe6 —— 本章基线候选仿真 PASS / valid（四项义务全过）
sim-0e581ab5dfd2 —— 第 08 章 seg-counter 增量仿真 PASS / valid
sim-e73184add91f —— 第 09 章 btn-switch 增量仿真 PASS / valid
sim-c3fb67b7796d —— 教程首版全流程记录中的基线候选仿真 PASS

下一章你还会看到对应的原生构建证据 bld-7d8c71f1f588——两类证据各自独立，谁也不能替代谁。

知识 · verification.simulate 的动作语义

控制面亲跑，不是替你调脚本：它从冻结目录重新推导候选身份、重编译 scoped Test IR、 在隔离 run 目录里亲跑 iverilog/vvp、解析事件、对账义务——你工作树里的任何改动都进不了这条链。

返回字段怎么读：ok:true 动作成功；status: PASS 义务全对账； scope: CANDIDATE_SLICE 只验证候选声明的文件；asset → QUALIFIED 是模块获得的质量等级。

STEP 5

晋级基线（candidate.promote）

这一步在做什么：把「仿真 PASS 的候选」安装成新基线——以后任何增量都以它为父。

candidate.promote → ok:true
  intent marquee-baseline → PROMOTED
  asset module:marquee10  → BASELINE
  baseline digest: e2465585…   （7 个文件的新基线清单）
看什么晋级后 .evoverse/control/artifacts/baselines/<digest>/ 出现完整基线快照 （SYSTEM.md + 7 个文件的当时字节）。注意：快照是晋级那一刻的字节。
✓ marquee-baseline PROMOTED · module:marquee10 → BASELINE
知识 · 仿真过 ≠ 综合过

第 06 章我们会发现：这份基线快照里的 RTL 还带着一个综合器不认的语法—— 这正是「仿真过 ≠ 综合过」的活教材。仿真证据（本章）与原生构建证据（下一章）各自独立， 一个 PASS 换不来另一个 PASS。

小结与预告

候选链闭环：冻结 → 真跑 → 晋级。下一章把它变成比特流：Efinity 命令行的正确打开方式、 一个真实的综合错误（int 类型），以及 ISF「引导 + 重放两连 PASS」的验证仪式。
