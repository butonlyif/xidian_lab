CHAPTER 04

意图与规格

控制面全链第一段：intent.create → 仿真等级 → 密封规格包 → spec.draft / spec.approve。

本章目标

为「10-LED 跑马灯基线」走通控制面前半程，理解 EXECUTABLE_2_0 规格包的十个文件， 并且掌握「16 条 GENERATION_NOT_READY」这类规格错误的排障方法。

先建立心智模型：谁在管流程？

EvoVerse 的可靠设计流程由一个控制面（Project Control Plane）统一驱动。你（通过 Trae）只做三件事：

读状态 → 读动作 → 执行选定动作 → 重读 revision        # 每次只推进一个动作
动作作用本章出现？
project.initialize初始化工程身份（按 git 根）✓

STEP 1

建立意图（intent.create）

这一步在做什么：把「我要干什么」变成一条受管的意图记录；控制面同时把当前基线文件清单快照进去。

💬 对 Trae 说（点右侧按钮复制；注意开头带 @evoverse）：
@evoverse 我想做的第一个功能是个跑马灯：板上十个灯轮流点亮，每秒走八步这样循环，先把它做成第一个正式版本。

成功后状态里能看到意图变为 ACTIVE，revision 前进。

✓ 意图 ACTIVE · revision 前进
状态

revision 是每个成功动作都会推进的 64 位十六进制值，失败不推进——这是判断「动作到底成没成」的硬指标。

知识 · 为什么以 @evoverse 开头

这条前缀是进入 EvoVerse 标准设计流程的入口——它把消息路由到项目控制面（Project Control）， 你的文字会被当作设计意图来处理，而不是普通闲聊。

工程一旦受管（项目里出现 .evoverse/ 状态），AI 每轮对话都会自动读取项目状态、按流程推进， 所以后面的所有话术都不用再加前缀，直接说你想做什么就行。

万一新开会话时 AI 没接上流程，再说一次 @evoverse 把控制面唤起来即可。

STEP 2

选定仿真等级（两阶段决策）

这一步在做什么：控制面按风险事实推荐一个仿真等级，你确认后才允许起草规格。

💬 对 Trae 说（第一阶段：提交风险事实拿推荐）：
这个设计挺简单的，就一个时钟，没什么跨时钟域之类的东西，仿真怎么安排你看着推荐就行。
💬 对 Trae 说（第二阶段：确认选择）：
就按推荐的来。
✓ 推荐 FPGA_FUNCTIONAL · 已确认
状态 · 实测返回

触发因素只有 single-clock，推荐 FPGA_FUNCTIONAL， 阻塞义务 = reset + main-flow + critical-boundary + integration-smoke （恰好 3 个核心场景 + 1 边界 + 1 冒烟的预算上限）。

知识 · 等级决定义务预算

等级不是形式：它决定规格里要写多少验证场景。等级越低义务越少，但延期事项会被明确记录， 仿真结论也会带上等级限定——「这个 PASS 只代表功能级」。

STEP 3

写 EXECUTABLE_2_0 规格包（十个文件）

这一步在做什么：把「跑马灯怎么做」整理成一份可执行的契约，然后密封登记。

💬 对 Trae 说：
帮我把这个跑马灯整理成正式的规格：灯怎么个轮流法、复位的时候是什么样、多久走一步都写清楚，上板要接哪十个灯也定下来。
spec/marquee-baseline/
├── system-spec.json                          # 系统视图：需求 REQ-1..4、实例、连接、时钟/复位域
├── modules/marquee10.module-spec.json        # 模块契约：参数/端口/内部数据对象/行为
├── materials/mat-stage0-top.material-contract.json  # 板级物料：stage0 顶层（ADAPT_REQUIRED）
├── algorithms/algo-onehot-rotate.algorithm-spec.json # 算法：步骤/公式/数值策略/参考模型
├── verification/scenarios.json               # 4 场景（各带 verificationRole）
├── verification/oracles.json                 # 4 判定器
├── verification/properties.json              # 4 性质（含 requiredActivations）
├── verification/coverage.json                # 2 覆盖项
├── decisions.json                            # 4 决策（status: ACCEPTED）
└── traceability.json                         # 需求 ↔ 场景/判定器/性质/覆盖 追踪

写完必须密封（seal），否则 digest 对不上：

python "C:\Users\<你>\evoverse-sdk\runtime\skills\evoverse-design-spec\scripts\seal_executable_spec.py" spec/marquee-baseline

{"manifestPath": "generation-manifest.json", "specPackageDigest": "ef9a502b...", "status": "SEALED"}
✓ 规格包 SEALED
知识 · 规格不是散文

EXECUTABLE_2_0 规格包是一份可执行的契约：需求、模块端口、算法、验证义务、决策、追踪，全部结构化。 下一章的仿真判定器就是从这里读「什么算对」。

密封器会重渲染 specification.md（人读版）、生成 generation-manifest.json 和包 digest。改任何文件后都要重新密封，否则 digest 对不上。

STEP 4

spec.draft：一次真实的 16 连错排障

这一步在做什么：把密封包登记进控制面。控制面的「生成就绪校验」比本地密封更严。

💬 对 Trae 说：
把 spec/marquee-baseline 这个包提交 spec.draft，绑定 marquee-baseline 意图。
翻车实录第一次提交被拒——packagePath 传了绝对路径；改成相对路径后， 又迎来 16 条 GENERATION_NOT_READY。逐条照着 jsonPointer 修完、重新密封、再次提交， 控制面接受，规格进入审批并获批。
✓ spec.draft ok · SPEC-001 APPROVED
修复 · 第一次拒绝

packagePath 传了绝对路径，控制面直接拒绝：

PACKAGE_PATH_ESCAPED: packagePath must be project-relative (reason: ABSOLUTE_PATH)

改成项目相对路径即可。

修复 · 16 条 GENERATION_NOT_READY

报错原文（jsonPointer 原样贴出）：

algorithms/...algorithm-spec.json#/numericPolicy/binaryPoint        必须声明 binary point
algorithms/...algorithm-spec.json#/numericPolicy/intermediateWidth     必须声明 intermediate width
decisions.json#/items/0..3/status  ×4                                决策必须 ACCEPTED 或 REJECTED
modules/...module-spec.json#/dataObjects/0,1/ownership  ×2             必须是 owned / observed
modules/...module-spec.json#/ports/1/clockDomain                       rst_n_i 也要绑定时钟域
system-spec.json#/connections/0,1/from  ×2                            连接两端都必须是 instance.port
system-spec.json#/connections/2/to  方向不匹配                          to 必须是输入端口
system-spec.json#/connections/2/to  宽度不匹配                         10 位总线不能接 1 位端口
system-spec.json#/connections/3/to                                    同上
verification/coverage.json#/items/0,1/rule  ×2                        覆盖项必须有可度量的 rule

逐条修法：numericPolicy 补 "binaryPoint": 0, "intermediateWidth": "NUM_LEDS"； 四个决策补 "status": "ACCEPTED"；ownership 改成枚举 "owned"； 复位端口补 "clockDomain": "clk_50m"；连接重建模——给板级物料的契约加一个 10 位输入端口 led_bus_i 承接总线（时钟/复位连接直接删除：控制面只强制 data 输入的连接性）； 覆盖项补 rule 文本。修完重新密封，再提交：

spec.draft → ok:true，SPEC-001 DRAFT，generationReady:true
spec.approve → SPEC-001 APPROVED（approvalDigest 56b22f18…）
知识 · 经验沉淀

本地密封通过 ≠ 控制面接受。两层校验各有分工——本地管「结构与渲染」， 控制面管「生成就绪」（枚举、方向、宽度、连接性、义务可度量）。报错都带精确 jsonPointer，照着改就行。

STEP 5

按规格写 RTL 与 testbench

这一步在做什么：把模块契约翻译成代码。规格里写死的名字（端口、参数、实例名 u_marquee）在这里必须一致。

💬 对 Trae 说：
规格定了，那就开始写代码吧：跑马灯本体做成一个模块，顶层把十个灯接出去，管脚从板卡资料里查；再配个仿真，平时仿真跑快一点没关系。
看什么本章过后工程里新增：rtl/marquee10.sv、改写的 rtl/top.v、 sim/tb_marquee10.sv、ISF 尾部多出的 9 组 assign、XML 里多出的一行 design_file， 以及 spec/marquee-baseline/specification.md（密封器渲染的人读版规格）。
知识 · 两个被规格约束的细节

复位期间全灭（REQ-2）：输出寄存 led_out_r 用异步复位清零，释放后 1 拍呈现 one-hot 初始码型； 内部逻辑用 3 级同步释放链——这正是「异步断言、同步释放」的双层写法。

仿真提速：顶层带 STEP_CYCLES 参数，testbench 例化时覆盖为 4（上板默认 6,250,000 = 8 Hz）。
