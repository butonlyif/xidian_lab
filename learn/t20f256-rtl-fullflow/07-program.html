CHAPTER 07

烧录与上板

一句话烧录上板：预期现象清单、板没连也不慌的排查路径。

本章目标

用自然语言让 AI 完成烧录；知道板连上之后应该看到什么（逐条可勾选）； 能区分「板没连」和「烧录失败」两类现象。

STEP 1

一句话烧录

这一步在做什么：把 outflow 里的比特流经板上 FT232HL 的 JTAG 口写进 FPGA （active 模式，掉电即失）。AI 会调好烧录工具链，你要做的只有两件物理的事： USB 线插到JTAG 口（别插到 USB 串口上）、打开板卡供电。

💬 对 Trae 说：
比特流出来了，帮我烧到板子上，烧完把结果告诉我。
知识 · active 模式：掉电即失

比特流经板上 FT232HL 的 JTAG 口写进 FPGA——active 模式，掉电即失； 要让板卡上电自动加载，走的是 SPI Flash 固化那条路（见 STEP 4 右栏）。

STEP 2

板没连时的真实报错（本教程实测）

翻车实录教程写作时板子没接，AI 原样转述了烧录工具的报错：FAIL + 一条 Python 异常。 确认这是「没找到板子」而非比特流问题，照右栏排查顺序检查物理连接， 再对 AI 说一句「板子插好了，再烧一次」即可——不用重跑编译。
⚠ 没找到板子 ≠ 比特流问题
修复 · 报错原文与翻译 
****** Python exception running: efx_run.py marquee-lab --prj --flow program
    :   FAIL
An exception occurred: list index out of range

翻译：JTAG 设备枚举列表是空的，工具取「第 0 台设备」时越界。这是「没找到板子」，不是比特流问题。 看到这条不用慌，更不用重跑编译。

可能 · 排查顺序（从最常见的开始）
  1. USB 线插的是不是 JTAG 口（板上 FT232HL 那个），别插到 USB 串口（CH340N）上；
  2. 设备管理器里有没有出现 FT232HL 的 USB 设备；
  3. 板卡供电开关/跳线是否打开；
  4. 换一根能传数据的 USB 线（很多线只能充电）。

查完任何一项，回头对 AI 说一句「板子插好了，再烧一次」即可。

STEP 3

连上板之后：预期现象清单（基线跑马灯版）

这一步在做什么：把「上板验证」拆成一条条可观察、可勾选的事实，而不是「看起来能跑」。 烧完别急着宣布成功，逐条对照。

#预期现象对应规格条款不成立时看哪里
1烧录完成后 LED1..LED10 按顺序逐个点亮，每 125 ms 前进一位（8 Hz），10 位一圈循环REQ-1（one-hot 跑马）若多个 LED 同亮/全灭交替 → 检查 led_bus 位序映射
2任意时刻只有一个 LED 亮PROP-ONEHOT多于一个 → 位宽/移位方向错
3按住 BUT1（A4 复位键）：10 个 LED 全部熄灭REQ-2（复位全灭）不全灭 → 输出寄存器的复位极性
4松开 BUT1：从 LED1 重新开始跑REQ-2（释放初始码型）从别处开始 → 复位值
5步进节奏稳定，无肉眼可见的抖动或跳变REQ-3（时钟使能分频）抖动 → 是否误用了分频时钟

💬 对 Trae 说：
板子上现象全对，把这次上板验证登记成证据。
⚠ 未连板 · programming / hardwareValidation 保持 NOT_RUN
状态 · 上板证据与 NOT_RUN 口径

AI 会用 hardware.validate 把场景清单登记为证据。教程环境没连板卡， 所以控制面证据向量里 programming / hardwareValidation 保持 NOT_RUN—— 这在工程语义上表示「尚未验证」，不得由编译成功或本清单推断为板上 PASS。

STEP 4

掉电与固化

这一步在做什么：交代 active 烧录的时效边界，以及「上电自动加载」要走哪条路——细节在右栏。

⚠ active 模式 · 掉电即失
知识 · 固化 = 写板载 SPI Flash

active 模式烧录的比特流掉电即失。要让板卡上电自动加载，需要把 .hex 写进板载 W25Q32 SPI Flash （管脚 N1/L3/M3/P3/G5 已在目录中预留），这属于后续迭代——本教程聚焦 SRAM 烧录。
