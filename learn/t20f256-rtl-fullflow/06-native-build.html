CHAPTER 06

原生编译

工程已经就位，一句话让 AI 完整编译并交付比特流；在 Workbench 里读懂编译结果与时序报告。

本章目标

不碰命令行：第 03 章建好的工程直接拿来编译——让 AI 跑完四阶段、把比特流交到你手上； 学会在 Workbench 里看编译报告（资源、管脚、时序、关键路径）；编译失败时，让 AI 照着日志自己修。

STEP 1

一句话触发编译

这一步在做什么：把 RTL 变成比特流要经过 Efinity 的四段流水线。这些全是 AI 的活，你只管说要什么。

💬 对 Trae 说：
工程已经建好了，RTL、仿真和约束都在里面，直接帮我完整编译一遍，最后给我一个能烧的比特流。

背后会发生三件事：① 直接复用既有工程文件——marquee-lab.xml（工程）、 constraints/*.isf（管脚）、constraints/*.sdc（时钟）在第 03 章就已落盘， 第 04 章的 9 组新管脚也已写进 ISF；② 依次跑 Efinity 的四个阶段； ③ 把结果汇总成报告。环境变量、工具路径这些脏活 AI 自己处理——你从头到尾不需要碰 efx_run.bat。

阶段在做什么产出
mapRTL 综合与技术映射（翻译成芯片原语）网表
interface重放 ISF 管脚约束 → 更新接口数据库marquee-lab.peri.xml（工程源文件）
pnr布局布线 + 静态时序分析时序报告、管脚报告
pgm生成比特流outflow\marquee-lab.bit / .hex
但这次编译失败了——这是真实发生的事，下一节看 AI 怎么修。
状态 · 编译

四阶段全绿后，比特流落在 outflow\marquee-lab.bit / .hex。 本次实测：这次编译在 map 阶段 FAIL——报错原文与修法见下一节的「翻车实录」。

知识 · 建工程只发生一次

第 03 章一句话建工程之后，就不会再有第二次「生成工程」了：基线晋级（第 05 章）后， 每一轮都是既有工程上的增量——编译复用现有 XML/ISF/SDC，增量意图开隔离 worktree， 集成也只是往同一个顶层继续例化。对 Trae 说「编译」就行，它认得这个工程。

知识 · 你只管说要什么

四段流水线（map → interface → pnr → pgm）全是 AI 的活：复用工程文件、跑阶段、汇总报告， 你从头到尾不碰命令行。efx_run.bat 一次都不用自己敲。

STEP 2

真实翻车：把报错丢给 AI

这一步在做什么：iverilog（仿真）和 Efinity（综合）对 SystemVerilog 的支持面不一样——「仿真过 ≠ 综合过」。 排错的方式不是你自己啃日志，而是让 AI 读。

💬 对 Trae 说：
编译失败了，你看看报错和日志，把问题修好，修完再编译一遍。
翻车实录这次编译在 map 阶段倒下：端口参数写成了 parameter int， iverilog 完全接受，Efinity 前端不认。把报错丢给 AI，它定位到三处方言差异，回归 Verilog-2001 等价写法。 修完自动重编，四阶段全绿： 
   map :        PASS
   interface :  PASS
   pnr :        PASS
   pgm :        PASS      # outflow\marquee-lab.bit / .hex 到手
✓ 修复后四阶段全绿 · 比特流到手
修复 · map 日志现场

AI 从 map 日志里找到的报错原文：

[EFX-0010 VERI-ERROR] 'int' is an unknown type (VERI-1556) (rtl/top.v:14)
[EFX-0010 VERI-ERROR] module 't20f256_xd_ps_eval_stage0' is ignored due to previous errors
   map :        FAIL

第二行说明顶层模块因前序错误被整体忽略——所以必须先修 rtl/top.v:14 那一个类型错。

修复 · 三处 V2001 改动

肇因：端口参数写成了 parameter int STEP_CYCLES = ...——iverilog 完全接受，Efinity 前端不认。 修法是回归 Verilog-2001 兼容写法，三处改动全部语义等价：

SV 写法（仿真器认）V2001 写法（综合器也认）
parameter int N = 10parameter N = 10
cnt <= '0;cnt <= 0;
led <= '0;led <= {NUM_LEDS{1'b0}};
知识 · 经验沉淀

报错原文是排错的第一手证据。把「编译失败了，你看看报错修一下」说给 AI， 比自己猜强得多——它读得到完整日志，也知道「int 换 V2001 写法」这类工具差异。

STEP 3

在 Workbench 里看编译结果与时序报告

这一步在做什么：编译结果不应只是「PASS 四连」，你要亲眼看到资源花了多少、管脚落在哪、时序过没过。

💬 对 Trae 说：
编译过了，把编译报告打开给我看看：资源用了多少，时序有没有过，管脚都落在哪。

AI 会打开 Workbench 的编译报告面板（也可以自己来：左侧活动栏点开 EvoVerse 的 Workbench → Build 标签 → 打开最近一次编译的报告）。报告按标签页分块，每页看一样东西：

标签页看什么基线跑马灯的实测值
概览四阶段 PASS/FAIL、总耗时、器件与顶层T20F256 / 全 PASS
资源FF / LUT / BRAM / DSP 占用与占比几十个 FF/LUT，占比不足 1%
IO 与时钟每个信号的管脚、电平、bank；时钟与约束clk_50m→H13、LED 首脚→T8 等落针核对
时序Setup/Hold 是否 MET、WNS（最差裕量）正裕量，Fmax 约 399.5 MHz（约束 20 ns）
关键路径最差路径的逐段图（Mermaid），能点到 RTL 行号计数器比较 → one-hot 译码
优化建议 / Tcl可执行的编译策略；本次编译实际执行的命令基线无需优化
✓ 报告面板打开 · T20F256 全 PASS
知识 · 看报告的肌肉记忆

先看概览确认真过了 → 看时序 WNS 是不是正数 → 再扫一眼资源有没有异常膨胀。

分支 · 时序没过时

去「关键路径」标签页：最差路径会画成逐段图（Mermaid）并链到 RTL 行号，直接从那里开始查。

STEP 4

AI 自动的安全仪式：ISF 重放验证

这一步在做什么：管脚约束文件（ISF）有「重放安全」契约——每次编译都会把 ISF 重放到工程的接口数据库上， 所以 ISF 只能写幂等的赋值语句，且改动后要过官方自检。这些 AI 每次都会做，你只需要知道为什么。

新管脚的首次编译是「引导」：接口数据库第一次认识这些实例，自检会先报一批 「Unknown instance」类警告（属预期，不是语法错）。这次实测的复验证据有两层： 编译的 interface 阶段 PASS——每次编译都会把 ISF 完整重放一遍，PASS 就是官方的「重放安全」证明； 再人工核对 peri.xml 的管脚数与电平无异常。完整版 SDK 另带 cli/import_gpio.bat --dry-run 可做独立自检：

[OK] No issues reported.      exit=0   # 完整 SDK 环境的独立自检输出

顺带一提：这次编译已作为 build.native 证据登记进控制面 （证据 ID bld-7d8c71f1f588，NATIVE_BUILT / PASS / valid），与第 05 章的仿真证据并列—— 仿真证据和原生构建证据各自独立，谁也不能替代谁。

✓ bld-7d8c71f1f588 已登记 · NATIVE_BUILT
你唯一要记住的：工程里的 marquee-lab.peri.xml 是工程源文件， 别手改、别删除——删了之后下一次编译的管脚约束就对不上了。这是本工程少数「不要碰」的文件。

知识 · 引导 vs 重放

引导（一次性）：首次编译时接口数据库第一次认识这些管脚实例， 自检先报一批「Unknown instance」类警告——属预期，不是语法错。

重放（每次）：ISF 只写幂等的赋值语句，每次编译的 interface 阶段都把 ISF 完整重放一遍—— 阶段 PASS 就是官方的「重放安全」证明。

👀 观察文件本章没有新增工程文件——marquee-lab.xml（Efinity 工程）、 marquee-lab.peri.xml（接口数据库，勿动）、constraints/ 下的 .pins.isf（管脚，Python API 格式） 与 .sdc（时钟约束）都是第 03 章起就存在的工程源文件，本轮原样复用。变化只在编译输出：每次编译后 outflow\ 被整组刷新——网表、pinout.rpt、timing.rpt、res.csv 和最终的 .bit/.hex。

小结与预告
