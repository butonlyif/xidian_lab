CHAPTER 11

排错手册

本教程踩过的每一个坑，按「症状 → 根因 → 解法」归档。全部来自真实运行。

本章目标

遇到同类报错时，能在 30 秒内在这里找到定位与修法；更重要的是学会「读错误原文找权威规则」的习惯。

本章用法：左栏对号入座——问题名、症状与报错原文都在左边，拿你屏幕上的报错来检索； 右栏拿药——红色「修法」卡片是逐条修复步骤，紫色「为什么会这样」卡片是根因解释。 条目按出错环节分成 A / B / C / D 四组。

A. 环境与工具链

efx_run.bat 直调即崩

调 efx_run.bat 即崩。

No module named 'encodings'
修法
  • 把报错丢给 AI 即可——SDK 走 EfinixAdapter 会自动补齐环境；
  • 手工排查可先跑 Efinity 的 setup.bat。
为什么会这样

Efinity 自带 Python 需要 PYTHONHOME，直调 bat 没有 setup 环境。

缺 EFINITY_USER_DIR_INI

An exception occurred: 'EFINITY_USER_DIR_INI'
修法
  • 交给 AI 处理；
  • 手工补： 
    $env:EFINITY_USER_DIR_INI = "$env:LOCALAPPDATA/efinity/user_dir.ini"
为什么会这样

缺该环境变量。

缺 EFXDBG_HOME（program 阶段）

An exception occurred: 'EFXDBG_HOME'
修法
  • 交给 AI 处理；
  • 手工补 EFXDBG_HOME 与 debugger\bin 的 PATH。
为什么会这样

debugger 组件路径未设。

iverilog 找不到 root module

代码明明没问题。

Unable to find the root module
修法

转回无 BOM 的 UTF-8：

[IO.File]::WriteAllText($p, [IO.File]::ReadAllText($p), [Text.UTF8Encoding]::new($false))

本教程实测 BOM（首三字节 EF BB BF）同样触发。

为什么会这样

文件被 PowerShell Set-Content 写成 UTF-16，或写成带 BOM 的 UTF-8——两种都会让 iverilog 认不出模块。

list boards 里没有 t20f256-xd-ps-eval

evoverse list boards 里没有 t20f256-xd-ps-eval。

修法
  • 先 evoverse catalog status 看回执（本教程要求 ≥0.9.6）；
  • 未同步就跑 evoverse.cmd sync；
  • 离线环境用 import-local 或把成型板卡文件夹放入 <SDK>\catalog\boards\。
为什么会这样

从未执行 evoverse sync，或 sync 的版本/频道不含该板卡。

import-local 报 already exists

already exists: …\catalog\boards\<id>
修法
  • 确认要覆盖再加 --force；
  • 或用 --id 新名字 导入为另一块板。
为什么会这样

同 id 板卡已存在（上次导入或 sync 装过）。

成型板卡包导入后骨架丢失

成型板卡包（含 jackets\）被 import-local 导入后骨架模板丢失。

修法

成型板卡目录直接放入 <SDK>\catalog\boards\<板卡id>\，不要走 import-local。

为什么会这样

import-local 按散件路由（isf 平铺进 constraints\），会打散已成型的 Catalog 目录结构。

B. Efinity 编译与约束

EFX-0010：'int' is an unknown type

[EFX-0010 VERI-ERROR] 'int' is an unknown type
修法

回归 V2001：parameter N = 10、<= 0、{W{1'b0}}。

为什么会这样

综合器前端不认 SV 的 int（iverilog 认）。

dry-run 报 Unknown instance（仅新端口）

Fail to assign package pin. Unknown instance xxx
修法
  • 先做一次引导编译（map 会从 RTL 推断新端口）；
  • 再复跑 dry-run 应 [OK] No issues。
为什么会这样

peri.xml 还不认识新 GPIO 实例——这不是语法错误。

gpio_rule_cfg_io_standard_valid 类 IO 标准报错

gpio_rule_cfg_io_standard_valid
修法

照抄模板字符串，别自己缩写成 "3.3 V LVCMOS"。

为什么会这样

Trion 的合法字符串是 "3.3 V LVTTL / LVCMOS" 整串。

烧录报 list index out of range

list index out of range
修法

第 07 章 STEP 2 的四步排查。

为什么会这样

JTAG 设备枚举为空（板没连/线不对）。

C. 控制面（项目流程）

PACKAGE_PATH_ESCAPED

PACKAGE_PATH_ESCAPED
修法

改工程相对路径，如 spec/marquee-baseline。

为什么会这样

packagePath 传了绝对路径。

GENERATION_NOT_READY（N 条 jsonPointer）

GENERATION_NOT_READY
修法
  • 照 jsonPointer 逐条修；
  • 重新密封；
  • 重新 spec.draft。
为什么会这样

控制面生成就绪校验比本地密封严：枚举、方向、宽度、连接性、可度量 rule。

SOURCE_CLOSURE_INVALID

SOURCE_CLOSURE_INVALID: referenced missing module …
修法

语义等价改写：外层括号 / 拆中间信号 / case 换三元链 / 文案里用 . 或 , 分隔。

为什么会这样

闭合检查的词法器把 IDENT IDENT ( 当例化：函数调用赋值、比较括号、endcase 后跟 if (、字符串里的词都会中招。

SPEC_APPROVAL_STALE

SPEC_APPROVAL_STALE: package root does not exist
修法

密封包同步到主根与相关 worktree（目录不冲突，可共存）。

为什么会这样

spec.draft 从 worktree 解析，approve/simulate 从「根」解析——多意图并行时两边都要有包。

SPEC_IDENTITY_MISMATCH

SPEC_IDENTITY_MISMATCH: digest does not match the requested specDigest
修法

对当前意图的包再 draft+approve 一次（同 digest 的新记录成为最新）再 simulate。

为什么会这样

resolve 只认「最新一条 APPROVED」；别的意图先 APPROVED 会挡住当前请求。

MAIN_WORKTREE_DIRTY / INTENT_WORKTREE_DIRTY

MAIN_WORKTREE_DIRTY / INTENT_WORKTREE_DIRTY
修法
  • 提交或清理；
  • 支撑文件（spec 包、.evoverse 运行件）用 .git/info/exclude 排除。
为什么会这样

worktree 有未提交/未跟踪变更。

SMUGGLED_DELIVERY_CHANGES

SMUGGLED_DELIVERY_CHANGES
修法
  • 分支提交只放 candidate.deliver 声明的文件；
  • 其余走 exclude。
为什么会这样

intent 分支提交里出现了候选未声明的文件（含 spec 包、run 工件）。

RETRY_BLOCKED

RETRY_BLOCKED: The same tool call failed twice
修法

修完问题后带新的 requestId 重发。

为什么会这样

MCP 宿主拦截完全相同的第三次调用。

同参数两连败后动作被拒

修法

每次重试前确认工作树/包/路径已按错误修复。

为什么会这样

失败不推进 revision；宿主防死循环。

D. 仿真与 testbench

FAIL PROP-HOLD

FAIL PROP-HOLD rotate=1 hold=5 exp=4
修法
  • 首转期望 = 周期+1 并注释；
  • 后续转仍是精确周期。
为什么会这样

输出寄存让首个码型呈现固定多 1 拍。

FAIL ORC-SEG-DECODE

显示上一个数字。

FAIL ORC-SEG-DECODE … seg=c0 exp=f9
修法

TICK ≥ 8×SCAN（贴近上板比例）+ 只对「稳定且未变」拍核对。

为什么会这样

数字变化拍的段码呈现滞后 1 拍；仿真参数让变化落进选通窗口。

verification.simulate 判 incomplete-coverage

本地 vvp 全 PASS 但 verification.simulate 判 incomplete-coverage。

修法
  • 对照 traceability 核对每个 ID 与 requiredActivations；
  • 事件行 JSON 必须完整可解析。
为什么会这样

某义务的事件行数不够，或出现了期望集之外的 ID（拼写/JSON 不完整都会丢行）。

消抖行为与预期差 1~2 拍

修法

以「btn_i 低电平拍数」为激励计量单位设计期望。

为什么会这样

两级同步链的延迟在计数窗口里。

一条元技能：所有 C 类错误的第一手解释都在引擎源码里（evoverse_verification 包）。 把错误码原样交给 Trae 并要求「读引擎源码后给出语义等价的修复」——本教程所有疑难都是这样解掉的， 没有靠猜。

小结

坑分四类：环境（变量/编码）、工具链（方言差异）、流程（控制面的权威校验）、设计（时序边界）。 前三类靠手册速查，第四类靠规格里写清楚的边界条款。
