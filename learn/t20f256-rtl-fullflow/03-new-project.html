CHAPTER 03

创建第一个工程

一句话生成 stage0 骨架，一次真实编译证明工具链健康。

本章目标

得到 marquee-lab 工程（骨架：50 MHz 时钟 + 复位按键 + 1 个 LED 的闪烁设计）， 并看到 Efinity 四阶段编译全部 PASS。

STEP 1

打开 Welcome 界面，完成环境设置与体检

这一步在做什么：Welcome 页是 SDK 的控制台首页——环境体检、Catalog 同步、板卡画廊、各功能入口都在这里。 开工之前先在这里把环境设置收尾，比在命令行里逐项猜要直观得多。

# 在 Trae 里按 Ctrl+Shift+P 打开命令面板，输入：
EvoVerse: Show Welcome
✓ 体检全绿 + Catalog 统计里能看到板卡数——可以开工了
状态 · 体检面板查六项

页面上半部分是环境体检面板，逐项检查 Python / Efinity / MCP / 仿真器 / CLI / 适配器—— 全绿说明第 01 章的环境就位。

修复 · 体检出现红项

有红项时点「重新体检」；路径类红项用命令面板 EvoVerse: Set Up (re-run bootstrap) 重跑一遍安装引导即可修正。

可能 · 两个入口提醒

扩展装好后通常会自动弹出 Welcome 页；没弹就用 EvoVerse: Show Welcome 随时打开。

右侧是 Catalog 统计与 Sync Catalog 按钮——第 01 章的 sync 也可以直接在这里点 （命令面板同样有 EvoVerse: Sync Catalog / EvoVerse: Catalog Status）。

STEP 2

用自然语言建工程

这一步在做什么：SDK 从板卡目录挑出骨架 jacket，落成一份可以直接编译的 Efinity 工程—— 这是工程生成能力，还不涉及后面的「设计意图」流程（那个入口在第 04 章）。

💬 对 Trae 说（点右侧按钮复制）：
帮我在这块 t20f256 的板子上新建一个工程，就叫 marquee-lab，先来个最简单能跑的设计，把编译的流程先走通。

Trae 会调用 SDK 的工程生成能力，产出下面这棵文件树（每一步生成新文件时，留意 👀 标记）：

marquee-lab/
├── rtl/
│   └── top.v                                  # 顶层：24 位计数器最高位驱动 led_user（~0.34 Hz 闪烁）
├── constraints/
│   ├── t20f256_xd_ps_eval_stage0.pins.isf     # 管脚约束（Python API 格式，含 7 组 bank 电压）
│   └── t20f256_xd_ps_eval_stage0.sdc          # create_clock -name clk_50m -period 20.000
├── marquee-lab.xml                            # Efinity 2026.1 工程（unified_flow=true）
├── marquee-lab.peri.xml                       # 接口数据库（工程源文件，构建后必须存活）
└── stage0.md                                  # 骨架说明（含管脚表与编译方法）
看什么打开 rtl/top.v：顶层模块名是 t20f256_xd_ps_eval_stage0， 端口只有 clk_50m / arst_n / led_user 三个。
✓ marquee-lab 工程落盘（rtl + ISF + SDC + XML + peri.xml）
知识 · ISF 不是 XML

打开 .pins.isf：里面是 design.assign_pkg_pin("clk_50m","H13") 这样的 Python 调用——ISF 不是 XML，这一点后面章节非常重要。

STEP 3

先做一次「工具链体检」编译

这一步在做什么：骨架设计的意义就是快速暴露环境问题——RTL 只有一行逻辑，编译失败必然是环境/工程问题而不是设计问题。

💬 对 Trae 说：
帮我把这个工程完整编译一遍，每个阶段成没成、报告放在哪，都告诉我。

Trae 在后台调 Efinity 工具链跑的编译（真实输出，本教程实测）：

   map :        PASS      # RTL 综合与技术映射
   interface :  PASS      # 重放 ISF 约束 → 更新 peri.xml
   pnr :        PASS      # 布局布线 + 静态时序分析
   pgm :        PASS      # 生成 bitstream / hex
看什么四行 PASS；时序报告里 Fmax 约 399.5 MHz（对 20 ns 周期约束裕量巨大）。
✓ map / interface / pnr / pgm 全 PASS
修复 · 最常见的三种失败

① ModuleNotFoundError: No module named 'encodings'——Efinity 的 Python 环境变量没设 （直接对 Trae 说「编译环境报错了，你看看怎么修」，或见排错手册 A 节）。

② An exception occurred: 'EFINITY_USER_DIR_INI'——缺该环境变量（同样交给 AI 处理）。

③ 烧录阶段 list index out of range——板子没连（→ 第 07 章专门讲）。

STEP 4

看懂三份关键报告

这一步在做什么：养成「编译完先看报告」的习惯；后面增量时你要能自己判断管脚冲突和资源余量。

outflow\marquee-lab.pinout.rpt    # 管脚报告：确认 H13/A4/T8 落针、无冲突
outflow\marquee-lab.timing.rpt    # 时序：Slack 为正 = 满足约束
outflow\marquee-lab.res.csv       # 资源：FF / LUT / RAM 使用量
看什么pinout.rpt 确认 H13/A4/T8 落针、无冲突；timing.rpt 的 Slack 为正；res.csv 里 FF / LUT / RAM 使用量。
知识 · 骨架的基线价值

骨架阶段的资源占用极小（几十 FF/LUT），但它建立了基线认知：后面集成完成时我们会回到 res.csv 对比三个模块各自的占用。

STEP 5

给工程做一次 git 初始化

这一步在做什么：EvoVerse 控制面按 git 根识别工程边界；第 08 章的并行增量还会用到 git worktree。

git init
git add -A
git commit -m "stage0 skeleton from new-project"
# 实测提交：2abc3b7（68 个文件）
看什么提交后工程根出现 .git\；第一次调用控制面时还会出现 .evoverse\control\（收据与工件目录）。
✓ 实测提交 2abc3b7（68 个文件）
知识 · 为什么这一步不能省

控制面按 git 根识别工程边界——骨架一落盘就 init + 首次提交， 后面的控制面动作才能正确圈定工程；第 08 章的并行增量还会用到 git worktree。

小结与预告

骨架编译通过 = 工具链健康证明。但从「能编译的骨架」到「受管的设计」，中间隔着一整套控制面流程： 意图（intent）、仿真等级、可执行规格（EXECUTABLE_2_0）。第 04 章我们把这层关系讲清楚—— 并且原样复盘一次 16 条规格错误的排障现场。
